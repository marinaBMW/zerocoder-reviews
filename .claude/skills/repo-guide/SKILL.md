# Скилл: гайд по работе с zerocoder-reviews

Маришка не технарь. Прежде чем делать — коротко объясни план и **спроси согласие**, только потом запускай скрипты или коммить.

## 1. Структура репозитория

```
zerocoder-reviews/
├── scripts/            — все Python-скрипты (парсеры, нормализация, аналитика, дашборд, monitor)
├── data/               — сырые данные (НЕ в гите, см. .gitignore)
│   ├── WebReviews/     — reviews-{площадка}.{csv,json}
│   ├── GC-Reviews/     — внутренние выгрузки GetCourse по курсам
│   └── unified-reviews.csv — сводный датасет после normalize
├── reports/            — готовые отчёты (в гите только финальный дашборд)
├── docs/               — гайды, исходники lesson-feedback (НЕ в гите)
├── tmp/                — рабочий мусор, отладка (НЕ в гите)
├── .claude/agents/     — 6 подагентов (review-normalizer, review-analyst,
│                         insights-extractor, dashboard-builder,
│                         response-drafter, review-parser)
├── .claude/skills/     — слэш-скиллы (этот файл — один из них)
├── CLAUDE.md           — правила работы в проекте
├── README.md           — публичное описание проекта
└── .gitignore
```

## 2. Запуск сервиса

### Через скиллы (предпочтительный путь)
- `/reviews-refresh` — пересобрать дашборд по свежим данным (normalize → analyze → insights → dashboard).
- `/reviews-unanswered` — отчёт по неотвеченным внешним отзывам + черновики ответов.
- `/reviews-parse-otzovik` — полный перепарсинг Отзовика (~5 часов).

### Прямые команды
- Один парсер: `python scripts/parse-{площадка}.py` (площадки: `2gis`, `kurshub`, `okursah`, `otzovik`, `pgdv`, `skill2go`, `tutortop`, `yandex-maps`, `irecommend-interactive`, `otzovik-interactive`).
- Нормализация: `python scripts/normalize-reviews.py` → `data/unified-reviews.csv`.
- Аналитика: `python scripts/analyze-reviews.py` → `tmp/dashboard-data.json`.
- Сборка дашборда: `python scripts/build-reviews-dashboard.py` → `reports/{date}-reviews-dashboard.html`.
- Аналитический дашборд (общий): `python scripts/build-analytics-dashboard.py`.
- Неотвеченные: `python scripts/draft-unanswered.py`.
- Мониторинг новых отзывов: `python scripts/monitor.py` (требует `scripts/monitor-config.json` — он в `.gitignore`).

### Особые случаи
- **Otzovik / iRecommend** — интерактивные парсеры с обходом капчи. Запускать прямой командой в фоне, следить за файлом-флагом (`tmp/{site}-captcha-pending.txt`), снимать когда Маришка скажет «решила».
- **2ГИС** — `scripts/parse-2gis.py` сам не работает (SPA не рендерится в headless). Использовать MCP Playwright: `mcp__playwright__browser_evaluate` → сохранить JSON → дальше прогнать через нормализатор.
- **Google Maps** — Маришка обновляет вручную, не парсим.

## 3. Внесение изменений

### Правила нейминга (из CLAUDE.md, не нарушать)
- Файлы — `lowercase-with-dashes`. Кириллица в именах файлов и папок **запрещена**.
- Парсеры — `parse-{площадка}.py`.
- Файлы отзывов — `reviews-{площадка}.{csv,json}` в `data/WebReviews/`.
- Датированные снимки — `YYYY-MM-DD-...` в начале (`2026-06-15-reviews-dashboard.html`).
- Подагенты — в `.claude/agents/{kebab-case}.md`.
- Скиллы — в `.claude/skills/{kebab-case}/SKILL.md`.

### Схема данных (единая для всех источников)
Поля в каждом `reviews-{площадка}.{csv,json}`:
`date, name, rating, title, text, pros, cons, reply, url, source_page`.
Сортировка — новые сверху.

### Что нельзя делать
- **Удалять, переименовывать или редактировать файлы в `data/` без явного согласия Маришки.**
- **Отвечать на отзывы** или отправлять сообщения от её имени — мы только готовим черновики.
- **Добавлять новую площадку самостоятельно.** При нахождении нового источника — сообщить в чате со ссылкой и кратким описанием, дождаться согласования.
- Использовать кириллицу в именах файлов.
- Действовать через её Google-аккаунт сверх явно подтверждённого (подтверждено: только email-отчёт от `monitor.py`).

### Как добавить новый парсер
1. Создать `scripts/parse-{площадка}.py` — следовать структуре существующих парсеров (`parse-tutortop.py` для статики, `parse-okursah.py` для Playwright).
2. Сохранять результат в `data/WebReviews/reviews-{площадка}.{csv,json}` по единой схеме.
3. Прописать площадку в `scripts/normalize-reviews.py` (источники).
4. Обновить таблицу в `README.md` (счётчик отзывов, особенности).
5. Прогнать `/reviews-refresh` чтобы новые отзывы попали в дашборд.

## 4. Обновление README.md

README обновляем когда:
- Появился новый парсер или площадка — обновить таблицу площадок и счётчики.
- Изменился MVP-функционал (добавилась/убралась функция).
- Поменялись технологии (новая библиотека, отказались от старой).
- Изменилась команда запуска или путь к дашборду.

**Что НЕ менять:** структуру разделов (Проблема / Пользователь / Основная функция / Формат результата / MVP / Технологии) — это согласованный с Маришкой формат.

После правки — показать дифф, спросить согласие, потом коммитить.

## 5. Проверка ошибок

Перед тем как сказать «готово»:
- Скрипт реально запустился без exception (проверить `echo $?` или код возврата).
- На выходе появился ожидаемый файл с непустым содержимым.
- Счётчики совпадают (например, после парсера `wc -l reviews-{x}.csv` ≈ количеству, объявленному в логе).
- Если ошибка площадки (капча, авторизация, блок) — **прямо сказать Маришке**, не молчать и не выдумывать данные.

Если ломается скрипт — сначала прочитать стектрейс целиком, искать корень. Не глушить ошибки `try/except: pass`.

## 6. Подготовка к публикации (git push)

Чек-лист перед коммитом в публичный репо `marinaBMW/zerocoder-reviews`:

1. **`git status --short`** — убедиться, что в стейдже нет:
   - ничего из `data/` (даже случайно)
   - `reports/*` кроме разрешённого в `.gitignore` финального дашборда
   - `tmp/`, `.playwright-mcp/`, `*-debug.html`, `*.png`, `*.log`
   - `scripts/monitor-config.json` (содержит Gmail App Password)
   - `.mcp.json`
2. **Поиск секретов в дифе** — `git diff --cached | grep -iE "password|token|api[-_]?key|secret"`. Если что-то найдено — не коммитить, спросить Маришку.
3. **Проверить README на актуальность** — если менялись скрипты или площадки.
4. **Коммит** — осмысленное сообщение в одну строку («что» и «зачем»), без `Co-Authored-By` (репо личный, не нужно).
5. **Push** — `git push`. После пуша дать Маришке ссылку на коммит/PR.

Если случайно закоммитили секрет — **не пушить**, сразу сказать Маришке, перевыпустить секрет, переписать историю (`git reset --soft HEAD~1` для последнего коммита) и повторить чек-лист.

## 7. Финальный отчёт Маришке

После любого изменения коротко:
- Что сделано (одна строка).
- Какие файлы изменились / появились.
- Что осталось / что заблокировалось.
- Если был push — ссылка.

Без длинных вступлений и пересказов очевидного.
